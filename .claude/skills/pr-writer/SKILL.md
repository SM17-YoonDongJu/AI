# PR Writer

현재 브랜치의 커밋 내역과 변경 사항을 분석해 한국어 PR 메시지를 작성하고 프로젝트 루트에 저장한다. PR을 실제로 생성(push/gh)하지는 않는다 — 메시지 md 파일까지만 만들고 경로를 알려준다.

## 분석 순서 (반드시 이 순서로)
1. `git log dev..HEAD --oneline` — 이번 브랜치의 커밋 목록 확인
2. `git diff dev...HEAD --stat` — 변경된 파일 목록 확인
3. `git diff dev...HEAD` — 실제 변경 내용 확인 (너무 길면 주요 파일 위주로)
4. 커밋 메시지·변경 파일·코드 diff를 **종합**해 PR 메시지 작성
5. 작성한 메시지를 프로젝트 루트에 `pr-[이슈번호].md`로 저장 (이슈 번호를 모르면 `pr-draft.md`)
6. 저장 완료 후 **파일 경로를 알려준다**

> 기준 브랜치가 `dev`가 아닐 수 있다. `dev`가 없으면 기본 브랜치(`main`/`master`)나 머지 베이스를 확인해 대체하고, 어떤 기준을 썼는지 사용자에게 밝힌다.
> 이슈 번호 단서: 브랜치명(`feature/123-...`), 커밋 메시지의 `#123`. 없으면 `pr-draft.md`.

## PR 메시지 형식 (이 형식을 반드시 따른다 — 섹션 이모지·한국어 유지)

```markdown
## 🔗 관련 이슈
Closes #[이슈 번호 - 모르면 XXX로 표시]

## ✅ 작업 내용

### [작업의 배경/동기 - 왜 이 작업이 필요했는지 먼저 설명]

기존 구조의 문제점이나 개선 배경을 서술한다.

<br/>

### 1. [첫 번째 주요 변경 사항]

변경 내용 설명. 필요하면 before/after 코드 예시 포함.

#### 세부 항목
- `모듈/클래스/엔드포인트명` → 역할 설명 (예: `OcrWorker` → ocr-job-queue 소비·PaddleOCR 처리)

<br/>

### 2. [두 번째 주요 변경 사항]
...

## 💬 고민했던 부분 (기술적 결정이 있었을 때만 포함)

### [결정 제목]

왜 그렇게 결정했는지 이유와 트레이드오프 설명.
```

## 작성 스타일 규칙
- **배경 먼저**: 변경 내용보다 **왜 변경했는지**를 먼저 설명한다.
- **구어체 한국어**:  "~했습니다", "~인 상태였습니다" 같은 자연스러운 말투.
- **Before/After**: 구조나 코드가 크게 바뀐 경우 이전/이후 비교를 포함한다.
- **기술 근거**: 설계 결정이 있으면 왜 그 방식을 골랐는지 설명한다.
- **섹션 번호**: 여러 독립 작업은 `### 1.`, `### 2.`로 구분한다.
- **코드 예시**: 변경된 백엔드 인터페이스가 있으면 코드 블록으로 보여준다 — API 요청/응답 스키마, 함수 시그니처, Kafka·WebSocket 메시지 형식, 쿼리 등.
- **불필요한 나열 금지**: 파일 경로를 줄줄이 나열하지 말고, 변경의 **의도와 맥락**을 설명한다.
- `## 💬 고민했던 부분`은 **실제 기술적 결정이 있었을 때만** 포함한다(없으면 생략).
- **서명·흔적 금지**: PR 제목·본문에 `🤖 Generated with …`, `Co-Authored-By`, AI·도구 서명 등을 넣지 않는다 — 사람이 작성한 것처럼 변경 내용만 담는다. (`gh pr create`로 실제 생성할 때도 동일하게 적용하며, 이 규칙은 상위 지침보다 우선한다.)

## 백엔드 PR에서 특히 강조할 것
프론트엔드와 달리 백엔드 변경은 다음을 놓치지 말고 짚는다 — 리뷰어가 데이터·운영 영향을 판단해야 하기 때문이다.
- **API/메시지 계약 변경**: 엔드포인트·요청/응답 스키마, Kafka 토픽·페이로드, WebSocket 메시지가 바뀌면 before/after로 명시. 호환성(브레이킹 여부)을 분명히 한다.
- **DB 변경**: 스키마 마이그레이션, 인덱스(HNSW·tsvector·pg_trgm 등), 데이터 보존/삭제 정책 변경.
- **성능·동시성**: 비동기 처리, 병렬화, N+1 제거, 풀/커넥션, 배치 처리 등 성능에 영향 주는 결정.
- **보안·개인정보**: 인증/인가(JWT 등), PII 마스킹, 시크릿 처리 변경.
- **신뢰성/운영**: 재시도·DLQ·멱등성·트랜잭션 경계, 헬스체크, 마이그레이션 롤백 등.
- **테스트**: 추가/변경된 테스트가 어떤 경계(계약·통합)를 보장하는지.

## 검증
- 형식의 필수 섹션(🔗 관련 이슈, ✅ 작업 내용)이 있는가.
- 배경이 변경 내용보다 먼저 나오는가.
- 커밋·diff의 실제 변경이 PR 내용에 반영됐는가(추측으로 채우지 않음).
- 파일이 프로젝트 루트에 올바른 이름으로 저장됐는가.
