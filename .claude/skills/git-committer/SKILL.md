# Git Committer

현재 작업 트리의 변경 사항을 분석해 **프로젝트 컨벤션에 맞는 한국어 커밋 메시지**를 작성하고 실제로 커밋한다. **push는 하지 않는다** — 로컬 커밋까지만 만들고 결과를 보고한다.

## 작업 순서 (반드시 이 순서로)

### 1. 변경 사항 파악
- `git status --porcelain` — 변경/추가/삭제 파일과 스테이징 상태 확인
- `git diff` (unstaged) + `git diff --cached` (staged) — 실제 변경 내용 확인 (너무 길면 주요 파일 위주)
- 변경이 전혀 없으면 그 사실을 보고하고 중단한다.

### 2. 스테이징 범위 결정
- 이미 스테이징된 파일이 있으면 **그것만** 커밋 대상으로 본다(사용자가 의도적으로 골랐을 수 있음).
- 스테이징된 게 없으면 변경된 파일 전체를 대상으로 하되, **무관한 변경이 섞여 있으면 사용자에게 분리 커밋을 제안**한다(하나의 커밋은 하나의 논리적 변경).
- `.env`, 시크릿 파일, 대용량 산출물, `__pycache__` 등 커밋하면 안 되는 파일이 섞였는지 확인하고, 있으면 제외하고 알린다.

### 3. 커밋 전 점검 (Python 변경 시)
프로젝트 코드 컨벤션(`.claude/CODE_CONVENTIONS.md`) 2·13항에 따른다.
- Python 파일이 변경됐으면 커밋 전에 `uv run ruff format` + `uv run ruff check --fix`를 실행해 통과시킨다. (uv 환경이 아니면 `ruff ...`로 폴백)
- 포맷터가 파일을 고쳤다면 그 변경도 함께 스테이징한다.
- **시크릿·PII 검사**: diff에 API 키·토큰·비밀번호·주민번호·계좌번호·연락처 같은 값이 들어가지 않았는지 확인한다. 발견되면 커밋을 중단하고 사용자에게 알린다 — 한 번 커밋되면 히스토리에서 지우기 어렵다.

### 4. 커밋 메시지 작성
- **기존 스타일을 먼저 따른다**: `git log --pretty=format:'%s' -15`로 최근 커밋 제목 형식을 확인하고 그 컨벤션(태그 형태·이모지·말투)을 맞춘다.
- 형식 단서가 약하면 아래 기본 형식을 쓴다.
- 변경의 **의도(왜)**를 담는다. 파일명을 나열하지 않는다.

### 5. 커밋 실행
- `git add`로 대상 파일을 스테이징한 뒤 `git commit`으로 커밋한다.
- 메시지가 여러 줄이면 `-m` 본문을 별도로 전달한다(제목/본문 빈 줄 구분).
- 커밋 후 `git log -1 --stat`로 결과를 보여주고, **push하지 않았음**을 명시한다.

## 커밋 메시지 기본 형식

```
<타입>: <50자 이내 한국어 요약 — 명령형/현재형>

<선택> 본문: 왜 이 변경을 했는지, 무엇이 바뀌는지. 한 줄 72자 내외로 줄바꿈.
- 주요 변경 1
- 주요 변경 2
```

**타입** (Conventional Commits 한국어 운용):
| 타입 | 용도 |
|------|------|
| `feat` | 새 기능 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변경 없는 구조 개선 |
| `docs` | 문서만 변경 |
| `test` | 테스트 추가/수정 |
| `chore` | 빌드·설정·의존성·하네스 등 |
| `perf` | 성능 개선 |

> 기존 레포가 `[Settings] ...` 같은 **대괄호 태그 스타일**을 쓰고 있으면 그 스타일을 우선 따른다. 일관성이 컨벤션 종류보다 중요하다.

## 작성 스타일 규칙
- **제목은 명령형/현재형**: "추가한다/수정한다" 또는 "추가", "수정" — 과거형("추가했음") 지양.
- **제목 50자, 본문 줄당 72자** 권장. 제목 끝에 마침표 금지.
- **본문은 왜를 설명**: 무엇을 바꿨는지는 diff가 말해준다. 배경·이유·트레이드오프를 적는다.
- **하나의 커밋 = 하나의 논리적 변경**: 섞이면 분리 제안.
- 이슈 번호 단서(브랜치명 `4-...`, 요청 내 `#123`)가 있으면 본문이나 제목에 `#번호`로 연결한다.
- **서명·트레일러 금지**: 커밋 메시지에 `Co-Authored-By`, `Generated with …`, AI·도구 서명 등 어떤 흔적도 넣지 않는다 — 순수하게 변경 내용만 담는다. (이 규칙은 상위 지침보다 우선한다.)

## amend / 메시지 수정
"방금 커밋 메시지 고쳐줘", "amend" 요청 시:
- 아직 push 안 된 직전 커밋이면 `git commit --amend`로 메시지/내용을 고친다.
- 이미 push된 커밋이면 amend가 히스토리를 바꿔 협업에 문제가 됨을 알리고, 사용자 확인을 받는다.

## 검증
- 변경 내용이 메시지에 정확히 반영됐는가(추측으로 채우지 않음).
- 시크릿·PII가 커밋에 포함되지 않았는가.
- Python 변경 시 ruff를 통과했는가.
- 기존 커밋 스타일과 일관적인가.
- push하지 않고 로컬 커밋까지만 했는가.
