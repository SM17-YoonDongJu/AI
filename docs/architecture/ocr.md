# OCR 워커 (02번)

> 출처: AI 엔진 아키텍처 문서 세트 · 최종 점검일 2026-07-15 · 브랜치 11-feature-langgraph-멀티에이전트-구현

## 🎯 한 문장 요약

업로드된 보험 문서(진단서·보험증권 등) 이미지를 **로컬 GPU에서 글자로 바꾸고**, 문서 종류를 알아내 필요한 정보를 뽑고, 개인정보를 가린 뒤 저장하고, 다음 단계(리포트 생성)에 넘기는 Kafka 워커다.

## 🌱 쉽게 말하면

사진 속 글씨를 컴퓨터가 읽을 수 있는 텍스트로 옮겨 적는 일을 **OCR(광학 문자 인식, Optical Character Recognition)** 이라고 한다. 사람이 종이 진단서를 눈으로 읽고 워드에 타이핑하는 걸 프로그램이 대신 해준다고 보면 된다.

이 워커는 그 타이핑 담당 직원이다. 다만 혼자 일하지 않고 **컨베이어 벨트(Kafka)** 앞에 앉아 있다. 벨트 위로 "이 파일 좀 읽어줘"라는 주문표가 흘러오면, 창고(S3)에서 해당 파일을 꺼내 글자로 바꾼다. 그다음 "이건 진단서구나" 하고 종류를 알아채고, 병명·보험사·금액 같은 중요한 항목만 골라 적는다. 마지막으로 주민번호·계좌번호처럼 민감한 개인정보는 검은 매직으로 지우듯 가려서(마스킹) 안전하게 창고 장부(PostgreSQL)에 넣고, 다음 직원(리포트 워커)에게 "준비 끝났어, 이제 네 차례야"라고 새 주문표를 넘긴다.

한 가지 원칙이 있다. **이 창고 밖으로 문서를 절대 내보내지 않는다.** 남의 회사(구글·아마존 같은 외부 OCR 서비스)에 사진을 보내 대신 읽게 하지 않고, 반드시 우리 회사 안 GPU 장비로만 처리한다. 진단서에는 병력 같은 민감정보가 가득하기 때문이다.

## 🚧 현재 구현 상태 — 스펙·골격 단계 (미구현)

솔직하게 말하면, **아직 실제로 돌아가는 OCR 코드는 없다.** 파일을 직접 확인한 결과는 이렇다.

| `src/ocr_worker/README.md` | 처리 흐름·계약·배포를 적은 설계 문서 | 🟢 스펙 있음 |

| PaddleOCR·분류·마스킹 로직 | **아직 없음** | 🔴 미구현 |

`__init__.py`의 전체 내용은 아래 한 줄이 전부다.

```python

```

Dockerfile도 마지막에 이렇게 정직하게 적어 두었다. 실행 진입점을 아직 안 만들었다는 뜻이다.

> 쉽게 말하면: 지금은 "이 직원이 뭘 어떤 순서로 해야 하는지"를 적은 업무 매뉴얼(스펙)과 "이 직원이 앉을 책상"(Docker 이미지 틀)까지는 준비됐지만, **정작 일하는 사람(코드)은 아직 출근 전**인 상태다. 아래 설명은 전부 "이렇게 동작하도록 설계했다"는 계획이며, 계약(입출력 형식)만은 코드로 확정되어 있다.

계약(주고받는 메시지 형식)만은 예외적으로 `src/core/contracts.py`에 실제 코드로 확정돼 있어서, 발행하는 쪽과 소비하는 쪽이 같은 형식을 쓰도록 강제한다. 이 부분은 아래 [입출력 계약](#-입출력-계약)에서 다룬다.

## 🛠️ 하는 일

이 워커가 (구현되면) 담당하는 일을 한 문장씩 풀면 이렇다.

1. **글자로 바꾸기** — 업로드된 진단서·보험증권 등의 이미지를 **PaddleOCR**(오픈소스 OCR 엔진, 로컬 GPU에서 실행)로 읽어 텍스트로 만든다. 한국어 모델을 쓰고, 표·인감·서명 영역까지 레이아웃을 분석한다.
2. **문서 종류 알아내기** — 첫 페이지 텍스트를 보고 이 문서가 진단서인지, 보험증권인지, 지급결과안내문인지, 청구서인지, 기타인지 판정한다.
3. **핵심 정보 뽑기(엔티티 추출)** — 종류에 맞게 진단명(KCD 코드로 매핑), 보험사명, 상품명, 지급금액 같은 항목을 골라낸다.

   > 용어 풀이: **KCD**는 한국표준질병사인분류로, "감기"처럼 사람이 쓰는 병명을 "J00" 같은 표준 코드로 바꾼 것이다. **엔티티(entity)** 는 문장에서 이름·날짜·금액처럼 의미 있는 조각을 가리킨다.

4. **개인정보 가리기(PII 마스킹)** — 주민번호·계좌번호·전화번호 같은 민감정보를 **정규식(글자 패턴 규칙)** 과 **NER(문맥으로 이름·기관 등을 찾아내는 AI 기법, Named Entity Recognition)** 로 찾아 가린다. 이렇게 가려진 텍스트만 다음 파이프라인(RAG·LLM)으로 넘어간다.

   > 용어 풀이: **PII(개인식별정보, Personally Identifiable Information)** 는 그 사람이 누구인지 특정할 수 있는 정보를 말한다.

5. **저장하고 넘기기** — 가려진 텍스트·문서 종류·추출한 항목을 `ocr_results` 테이블에 넣고, 다음 단계인 리포트 생성을 시작하라고 `report-job` 메시지를 발행한다.

> 쉽게 말하면: 사진 → 글자 → "무슨 서류지?" → "중요한 값만 발췌" → "민감정보는 검게 칠하기" → "장부에 기록하고 다음 사람 호출" 순서다.

## 🔒 왜 외부 OCR API를 안 쓰나

구글 비전(Google Vision)이나 애저 OCR(Azure OCR) 같은 외부 클라우드 OCR을 쓰면 코드는 훨씬 간단해진다. 그런데도 **일부러 안 쓴다.**

이유는 하나다. 보험 진단서에는 병력·주민번호 같은 극도로 민감한 개인정보가 들어 있는데, 이걸 외부 회사 서버로 전송하는 순간 **개인정보보호법 위반 소지**가 생긴다. 그래서 모든 OCR 처리를 **우리 회사 안 로컬 GPU 장비에서만** 수행한다. 문서 이미지는 회사 경계 밖으로 한 발짝도 나가지 않는다.

> 쉽게 말하면: 남의 집에 환자 진료기록을 맡겨 대신 읽게 하지 않고, 반드시 우리 병원 안에서만 열어본다는 원칙이다.

## 🔗 데이터 흐름 10단계

문서 한 장이 업로드되고 나서 완전히 처리되어 사라지기까지의 전체 여정이다.

1. **프론트엔드**가 멀티파트 폼으로 파일(PDF·JPG·PNG·TIFF)을 **SpringBoot**로 보낸다. (로드밸런서 ALB로 직접 진입)
2. **SpringBoot**가 로그인 토큰(JWT)을 검증한 뒤, 파일을 **S3에 암호화(SSE-S3)해서 저장**하고 Kafka에 작업 메시지를 발행한다.
3. 프론트엔드에는 곧바로 **202(접수 완료)** 를 돌려준다. 사용자는 기다리지 않는다.
4. **OCR 워커**가 Kafka(`ocr-job-queue`)에서 그 작업 메시지를 꺼내 온다.
5. S3에서 파일을 읽어 **PaddleOCR(로컬 GPU)** 로 텍스트를 뽑는다.
6. **문서 유형 분류 → 엔티티 추출 → PII 마스킹**을 차례로 한다.
7. 결과를 **PostgreSQL의 `ocr_results`** 에 저장한다.
8. 리포트 생성 파이프라인(05번)으로 결과를 넘긴다. (`report-job` 발행)
9. 손해사정사가 **서명을 완료**하면, 그 이벤트를 받아 `ocr_results`의 해당 레코드를 **삭제**한다.
10. S3에 남은 원본 파일은 **서명일 기준 3년 뒤 자동으로 만료**된다. (S3 Lifecycle 정책)

> 쉽게 말하면: 202는 "접수했어요, 결과는 알아서 처리해 둘게요"라는 대기표다. 사용자는 뒤에서 무슨 일이 벌어지는지 몰라도 되고, 나중에 리포트가 완성되면 그때 한 번 푸시 알림으로 통합 안내된다. (OCR 단계 자체엔 별도 알림이 없다.)

### 참고: 원래 계획에서 바뀐 부분

설계 문서에는 초기에 **FastAPI가 파일을 직접 수신**하는 안이 적혀 있었지만, 그 부분은 **취소선으로 폐기**되고 지금은 **SpringBoot가 게이트웨이(업로드·JWT·S3·Kafka 발행)** 를 맡는 것으로 확정됐다. 즉 파일 수신은 SpringBoot 담당이고, OCR 워커는 그 뒤 Kafka 소비부터 시작한다.

## 📋 입출력 계약

이 워커가 **무엇을 받아서(입력) 무엇을 내보내는지(출력)** 는 `src/core/contracts.py`에 파이썬 모델로 확정돼 있다. 발행하는 쪽과 소비하는 쪽이 서로 다른 형식을 쓰면 통합 버그가 나므로, **하나의 출처로 형식을 못 박아 둔** 것이다.

### 입력 — `OcrJob` (SpringBoot가 `ocr-job-queue`로 발행)

파일이 업로드될 때 SpringBoot가 만들어 보내는 "작업 주문표"다.

| 필드 | 뜻 | 비고 |
| --- | --- | --- |
| `job_id` | OCR 작업 식별자(UUID) | **멱등 키** |
| `s3_key` | 업로드 파일의 S3 위치 | 파일명은 UUID로 치환됨 |
| `content_type` | 파일 형식 | pdf·jpeg·png·tiff 중 하나 |
| `user_ref` | 사용자 참조(내부 식별자) | PII 아님 |
| `doc_type_hint` | 사용자가 고른 문서 유형 힌트 | 옵션(없어도 됨) |
| `claim_id` | `USER_CLAIMS.id` 참조 | 옵션 — report_worker가 조회 |
| `uploaded_at` | 업로드 시각(UTC, ISO-8601) | |

> 용어 풀이: **멱등(idempotent)** 은 같은 걸 여러 번 실행해도 결과가 한 번 한 것과 같다는 뜻이다. Kafka는 같은 메시지를 실수로 두 번 전달할 수 있는데(at-least-once, 최소 한 번 전달), 이때 `job_id`가 같으면 "아, 이미 처리한 작업이네" 하고 중복 처리를 막는다. 그래서 진단서가 두 번 OCR되어 장부에 두 줄로 쌓이는 사고를 방지한다.

이 계약의 실제 정의는 다음과 같다.

```python
class OcrJob(BaseModel):
    """Spring → `ocr-job-queue` → `ocr_worker`. 파일 업로드 시 발행되는 OCR 작업.

    토픽 `ocr-job-queue`, 파티션 키 `job_id`, at-least-once + `job_id` 멱등 처리.
    """

    job_id: str  # OCR 작업 식별자(UUID). 멱등 키
    s3_key: str  # 업로드 파일 S3 키(파일명은 UUID로 치환됨)
    content_type: ContentType
    user_ref: str  # 사용자 참조(내부 식별자, PII 아님)
    doc_type_hint: str | None = None  # 업로드 시 사용자가 고른 문서 유형 힌트
    claim_id: str | None = None  # USER_CLAIMS.id 참조(옵셔널) — report_worker가 조회
    uploaded_at: datetime  # 업로드 시각(UTC, ISO-8601)
```

허용되는 파일 형식(`ContentType`)은 딱 네 가지다. Spring 게이트웨이가 먼저 검증하지만, 워커도 진입점에서 한 번 더 확인한다.

```python
type ContentType = Literal[
    "application/pdf",
    "image/jpeg",
    "image/png",
    "image/tiff",
]
```

### 출력 ① — `ocr_results` DB 저장

가려진(마스킹된) OCR 텍스트, 문서 유형, 추출한 엔티티를 PostgreSQL `ocr_results` 테이블에 넣는다. **여기 들어가는 텍스트는 이미 PII가 가려진 상태**이며, 평문 개인정보는 저장하지 않는다.

### 출력 ② — `ReportJob` (`report-job`으로 발행 → 리포트 워커가 소비)

OCR·마스킹이 끝나면 "이제 리포트를 만들어라"는 새 주문표를 발행한다. 이게 **OCR 워커와 리포트 워커(05번)를 잇는 다리**다.

| 필드 | 뜻 | 비고 |
| --- | --- | --- |
| `report_id` | 리포트 식별자(UUID, 새로 생성) | **멱등 키** |
| `ocr_result_id` | `ocr_results.id` 참조 | 방금 저장한 그 레코드 |
| `job_id` | 원래 OCR 작업 추적용 | |
| `doc_type` | 분류된 문서 유형 | 아래 5종 중 하나 |
| `user_ref` | 사용자 참조 | |
| `claim_id` | `USER_CLAIMS.id` 그대로 전달 | 옵션 |
| `created_at` | 발행 시각(UTC, ISO-8601) | |

문서 유형(`DocType`)은 다섯 가지로 못 박혀 있고, 이 값은 `ReportJob.doc_type`과 `ocr_results.doc_type`이 함께 쓴다.

```python
class DocType(StrEnum):
    """분류된 문서 유형. `ReportJob.doc_type` 및 `ocr_results.doc_type`에 공유된다."""

    DIAGNOSIS = "diagnosis"  # 진단서
    POLICY = "policy"  # 보험증권
    PAYOUT_NOTICE = "payout_notice"  # 지급결과안내문
    CLAIM = "claim"  # 청구서
    OTHER = "other"  # 기타
```

> 쉽게 말하면: OCR 워커는 `OcrJob`이라는 주문표를 받아 일하고, 다 끝나면 `ReportJob`이라는 새 주문표를 만들어 리포트 워커에게 건넨다. 주문표에 `ocr_result_id`가 적혀 있어서, 리포트 워커는 "방금 처리한 그 결과"를 정확히 찾아갈 수 있다. **`claim_id`는 원래 청구 건과의 연결고리라 그대로 이어서 전달(패스스루)** 된다.

## 🌐 컴포넌트 간 통신 방식

| 구간 | 방식 |
| --- | --- |
| Frontend → SpringBoot | REST (multipart/form-data, ALB 직접 진입) |
| SpringBoot → S3 | AWS SDK (PutObject, SSE-S3) |
| SpringBoot → Kafka | Kafka Producer |
| OCR Worker → Kafka | Kafka Consumer (`ocr-job-queue`) |
| OCR Worker → S3 | AWS SDK (GetObject) |
| OCR Worker → PostgreSQL | asyncpg (Python) |

> 표 읽는 법: 왼쪽이 "누가 누구에게", 오른쪽이 "어떤 방법으로"다. **Kafka는 우체통** 같은 것이라, SpringBoot가 편지(작업 메시지)를 넣어 두면 OCR 워커가 자기 속도로 꺼내 간다. 둘이 동시에 붙어 있을 필요가 없어 한쪽이 바빠도 서로 기다리게 만들지 않는다. **S3는 파일 창고**, **PostgreSQL은 결과를 적는 장부**라고 보면 된다.

## 🗄️ 데이터 보존·삭제 정책

민감한 개인정보를 다루는 만큼, "언제까지 보관하고 언제 지우는지"가 법적으로 매우 중요하다.

| 데이터 | 보존 기간 | 삭제 트리거 |
| --- | --- | --- |
| S3 원본 파일 | 손해사정사 서명일로부터 3년 | 보험금 청구권 소멸시효(3년) 기준 만료 시 자동 삭제 |
| `ocr_results` (마스킹 텍스트·엔티티) | 리포트 확정 전까지만 유지 | 손해사정사 서명 완료 이벤트 발생 시 **즉시 삭제** |
| AI 리포트 초안 (JSONB) | 영구 보존 | 사용자 탈퇴 요청 시 별도 검토 |
| 최종 리포트 (PDF·DB 레코드) | 영구 보존 | 사용자 탈퇴 요청 시 별도 검토 |

> 표 읽는 법: 핵심은 **위 두 줄이 "임시 데이터"**, 아래 두 줄이 "영구 기록"이라는 점이다. 원본 이미지(S3)와 OCR 중간 결과(`ocr_results`)에는 개인정보가 담겨 있어 목적을 다하면 지운다. 반면 완성된 리포트는 손해사정사가 검수·서명한 공식 기록이라 남긴다.

**왜 이렇게 설계했나**

- **`ocr_results`를 서명 즉시 지우는 이유**: OCR 중간 결과는 리포트를 만들기 위한 재료일 뿐이다. 손해사정사가 최종 리포트에 서명하는 순간 그 재료는 쓸모를 다하므로, 개인정보를 더 들고 있을 이유가 없어 바로 삭제한다.
- **S3 원본을 3년 보관하는 이유**: 보험금 청구권의 소멸시효가 3년이라, 그 기간에는 분쟁이 생기면 원본을 확인해야 할 수 있다. 3년이 지나면 S3 Lifecycle 정책이 알아서 자동 만료시킨다.
- **AI 리포트 초안을 남기는 이유**: 손해사정사가 어떤 근거로 검수·서명했는지 추적할 수 있어야 하므로 DB에 보존한다.
- 전체적으로 **개인정보보호법의 "최소 수집·목적 외 보존 금지"** 원칙을 따른다. 필요한 만큼만 갖고, 목적을 다하면 지운다.

> 쉽게 말하면: 요리(리포트 만들기)를 하는 동안만 재료(원본·OCR 결과)를 냉장고에 두고, 요리가 완성되어 손님상에 나가면(서명 완료) 남은 재료는 바로 버린다. 완성된 요리 사진(최종 리포트)만 앨범에 영구 보관한다.

## 📦 의존성과 배포

- 이 워커는 공용 모듈 `core.kafka`(우체통 연결)·`core.db`(장부 연결), 그리고 S3와 **PaddleOCR**(`.[ocr]` extra의 `paddlepaddle-gpu`)에 의존한다.
- **PII 마스킹 규칙은 가드레일(06번) 입력단과 정렬**되어 있어야 한다. 두 곳에서 서로 다른 규칙으로 개인정보를 가리면 구멍이 생기기 때문이다.
- 배포는 `src/ocr_worker/Dockerfile`(CUDA 베이스 이미지)로 빌드해 **GPU 노드**에 올린다. PaddleOCR을 워커 프로세스 안에서 직접 돌리므로 반드시 GPU가 필요하다. (Ollama·vLLM 노드와 같은 장비에 함께 배치할 수 있다.)

Dockerfile의 핵심 부분은 이렇다.

```dockerfile
FROM nvidia/cuda:12.4.1-cudnn-runtime-ubuntu22.04 AS base
```

```dockerfile
# 의존성만 설치(프로젝트는 PYTHONPATH로 실행). uv.lock 커밋 후 --frozen 권장.
COPY pyproject.toml uv.lock* ./
RUN uv sync --no-dev --extra ocr
```

> 쉽게 말하면: **CUDA는 GPU에게 일을 시키는 통로**이고, 이 이미지는 그 통로가 깔린 리눅스 환경(`nvidia/cuda:12.4.1-cudnn-runtime`)에서 파이썬 3.12로 워커를 돌리도록 구성돼 있다. CUDA/cuDNN 버전은 실제 GPU 노드 및 `paddlepaddle-gpu` 휠과 맞아떨어져야 한다. 앞서 말했듯 실행 진입점(`__main__.py`)은 **아직 구현 전**이라, 지금 이 이미지를 빌드해 띄워도 실제 OCR 작업은 돌지 않는다.
